## 练习 1：去掉 curl 的 -N 有什么不同？

**我的回答**

返回的内容看不出区别，感觉去掉 -N 返回内容更多？更慢？

**点评** ⚠️ "内容看不出区别"对；"更多、更慢"不对。实测：
| | 首字节 | 总计 | 大小 |
|---|---|---|---|
| 加 `-N` | 0.72s | 1.53s | 2187B |
| 不加 | 0.55s | 1.42s | 2219B |
内容一样（大小差的 32 字节是两次回答本身不同），速度也一样：**数据到达 curl 的时间完全相同**。

`-N` 管的是 **curl 什么时候把收到的数据打印到屏幕**：
- 不加：curl 先攒进缓冲区，攒够一块或连接结束才一起打印，看起来"一下子全出来"
- 加：收到一点打印一点，能看到逐字出现
所以这道题的重点是：**流式要每一环都不缓冲**才有效。服务端、网关（如 Nginx 的 `proxy_buffering`）、客户端，任何一环攒着，用户都看不到逐字效果。上线时网关缓冲是最常见的坑。

"感觉内容更多"多半是因为不加 -N 时是一次性刷屏，看起来更多。

## 练习 2：Network 面板里 fetch 和 eventsource 有什么区别？

**我的回答**

非流式类型为 fetch，流式类型为 eventsource，有什么区别？启动器也不一样，大小也不一样，响应时间也不一样，还有哪些不同也展开讲讲。（截图：chat 0.7 kB、2.01 秒，启动器 stream.html:32；stream 4.1 kB、1.49 秒，启动器"其他"）

**点评** ✅ 四个不同都观察到了，逐个解释：

| 观察 | 原因 |
|---|---|
| **类型** fetch vs eventsource | 两种浏览器 API：`fetch` 是通用的"发请求、拿完整响应"；`EventSource` 是专门接 SSE 的，连接一直开着，每收到一个 `data:` 事件触发一次 `onmessage` |
| **启动器** stream.html:32 vs 其他 | fetch 是 JS 代码直接发起的，能定位到行号；EventSource 的请求由浏览器内部发起，所以显示"其他" |
| **大小** 0.7 kB vs 4.1 kB | 内容一样，流式多了包装：每个片段都有 `data:{"text":"..."}` 加空行，约 90 个片段 × 每个十几到二十字节。**流式更费流量**，换来的是更早看到 |
| **时间** 2.01 秒 vs 1.49 秒 | **不能说明流式更快**：两个请求同时发出，是两次独立的模型调用，回答长短不同，生成时间也不同（第 04 课笔记里多次实测：总时间基本一样）。流式真正的优势在"首字时间"，面板里的"时间"列是全部完成的时间 |

还有这些不同：
- **请求头**：EventSource 会自动带 `Accept: text/event-stream`；fetch 默认 `Accept: */*`
- **能力**：EventSource 只能发 GET、不能自定义请求头（没法带 `Authorization`）；fetch 都行。所以生产里很多人用 `fetch` + 读 `response.body` 的流来接 SSE，自己解析 `data:`
- **断线重连**：EventSource 断了会自动重连（服务端正常发完也算"断"，所以 `stream.html` 里要在 `onerror` 主动 `close()`，否则会不停重新提问、重复付费）；fetch 不会
- **EventStream 标签页**：只有 eventsource 请求有，能看到每个事件的到达时间，fetch 只有"响应"标签

## 练习 3：用户关网页后，服务端还会继续要内容、继续付费吗？

**我的回答**

应该会继续付费吧，用户关掉网页只是不再请求了，但是大模型处理还是需要的。验证：提问一个长问题，一个关页面，一个不关闭，看付费情况？

**点评** ⚠️ 结论不对，但**验证方法很好**，我就按你的方法做了：
| | 片段数 | 耗时 | 结果 |
|---|---|---|---|
| A：完整读完 | 802 | 7.96s | `complete`，最后一片 usage 350/800/1150 |
| B：1.5 秒后断开 | 84 | 1.51s | `cancel`，之后没有再收到任何片段 |

断开时发生了一连串的"取消"：
```
浏览器关闭 → Tomcat 发现连接断了 → Spring MVC 取消订阅 Flux
→ Reactor 一路往上游传 cancel → WebClient 关闭和 DeepSeek 的 HTTP 连接
→ DeepSeek 发现连接断了，停止生成
```
这是 Flux 的一个核心特点：**下游不要了，上游会知道**（背压/取消）。非流式 `.call()` 没有这个机制，用户关网页后照样会等模型写完。

关于付费，要分两层说：
- **我们这边能确定的**：B 只收到 84 个片段，取消后就不再读了
- **DeepSeek 那边按多少计费**：取决于服务端停得多快。一般按已生成的 token 计费，断开后可能还会多算一点点。我们拿不到 B 的 usage（usage 在最后一片，B 没等到），要核实只能去 DeepSeek 控制台对账单
- 你说的"大模型处理还是需要的"：服务端确实没法瞬间停，但不会傻傻写完 800 个 token

所以**流式在省钱上也有好处**：用户看到一半觉得不对、关掉重问，后半段就不用付了。

## 练习 4：用 .stream().chatResponse()，usage 在哪个片段？

**我的回答**

应该会在最后一片出现？作为所有生产结束的总花费。

**点评** ✅ 正确。实测 802 个片段里，只有第 802 片有值：`finishReason=STOP usage=350/800/1150`，前 801 片都是 0。
- 原因：开始生成时还不知道总共要写多少，只能写完再报总账
- 推论 1：**只要中途断开就拿不到 usage**（练习 3 的 B）。要精确统计用量，得自己数已收到的片段，或以厂商账单为准
- 推论 2：`.stream().content()` 只取文字，usage 直接丢了。需要统计时用 `.chatResponse()`，或者交给下一课的 Advisor 统一处理
- 小发现：800 个 completion token，正好被 `max-tokens` 卡住吗？不是，这次是 1024 上限、`STOP` 正常结束，说明模型自己写完了
- 对比：OpenAI 的接口默认流式不返回 usage，要传 `stream_options.include_usage=true`（truman-speaker 的 `takeEvalChatModel` 就是为这个加的 `streamUsage(true)`）。DeepSeek 默认就在最后一片返回

## 总结：第 04 课学到了什么
1. **流式 = 同样的速度，更早看到开头。** 总时间不变，首字时间提前；回答越长越值得
2. **每一环都不能缓冲**：服务端、网关、客户端，一处缓冲就退化成非流式（练习 1）
3. **流式的代价**：更费流量（练习 2，约 6 倍）、要处理 SSE 细节（空格被吃、自动重连）
4. **流式的额外好处**：用户断开时会一路取消到模型，不再生成剩下的内容（练习 3）
5. **usage 只在最后一片**，中途断开就拿不到（练习 4）

## 课外问答

**Q：`usage=350/800/1150` 三个值分别是什么？**
A：顺序是 promptTokens / completionTokens / totalTokens（实验代码里按这个顺序打印的）。
| 值 | 含义 | 这次的来源 |
|---|---|---|
| 350 promptTokens | **输入**：发给模型的全部内容 | system 人设（带示范，约 300）+ 用户问题 |
| 800 completionTokens | **输出**：模型生成的内容 | 回答正文；开思考时草稿也算在这里 |
| 1150 totalTokens | 两者之和 | 350 + 800 |
- 输入和输出**单价不同**，输出通常贵好几倍，所以要分开看
- DeepSeek 原始响应里还有 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`：同样的开头（比如人设）再次发送时可以命中缓存，命中部分更便宜。这些在 `nativeUsage` 里

**Q：传 `stream_options.include_usage=true` 在流式时有用吗？**
A：**对 DeepSeek 没用。** 绕过 Spring AI 直接调 DeepSeek 原始接口，三种写法各测一次：
| 请求 | usage 出现在 |
|---|---|
| 不传 | 最后一片（第 36 片） |
| `include_usage: true` | 最后一片（第 49 片） |
| `include_usage: false` | 最后一片（第 40 片） |
- DeepSeek 无论传什么，都在最后一片返回 usage，这个参数被忽略
- 而且 Spring AI 2.0.2 的 `DeepSeekApi.ChatCompletionRequest` 里**根本没有这个字段**，想传也传不进去（源码注释里提到了 `StreamOptions.includeUsage`，是从 OpenAI 模块抄过来没删的）
- OpenAI 不一样：默认流式**不返回** usage，必须传 `include_usage: true`，而且 usage 放在一个 `choices` 为空的额外片段里。truman-speaker 的 `streamUsage(true)` 就是为 OpenAI 协议加的
- 教训：各家号称"兼容 OpenAI 协议"，细节并不完全一样，以实测为准

**Q：Spring AI 是怎么统计流式 usage 的？**
A：读了 2.0.2 源码，分三步：
1. **每一片单独转换**（`DeepSeekChatModel.internalStream`）：这一片带 usage 就用它，不带就是 `EmptyUsage`（0/0/0）。所以前 801 片都是 0
2. **`UsageCalculator.getCumulativeUsage`**：名字叫"累加"，但累加的是**多轮调用**之间的（工具调用时模型会被调好几轮，第 09 课），不是同一次回答的各个片段之间
3. **`MessageAggregator`**：把所有片段拼成一个完整的 `ChatResponse`，交给观测（第 15 课的指标就从这里来）。它对 usage 的处理是**记住最后一个非 0 的值**，不是把每片相加

所以结论是：**usage 是厂商算好、在最后一片一次性给的，Spring AI 只是转交，不自己数 token。** 中途断开时最后一片没到，Spring AI 那边就是 0。
